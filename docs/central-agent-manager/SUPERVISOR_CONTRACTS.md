# Supervisor contracts

Local policy only. These modules do not start sessions, call the Cursor SDK, write a database, publish, send notifications, or change a live schedule.

Protected operation ids are imported from `src/lib/engineering/policy.ts`. Marketing publication, notification send, and live schedule changes keep their own operation ids. Each one uses that module's `external_publish` gate, and an approval for one id does not authorize another. The engineering worker remains the execution authority.

## What these checks establish

`evaluateExecution` is the execution-eligibility decision. `enterExecution`, `openSession`, and `confirmSessionRunning` call it again. A previous `{ outcome: "allowed" }` object is not an input and cannot start work. `transitionTask` cannot enter `running` or `completed`. `transitionSession` cannot enter `running`. `completeTask` requires verified evidence for the task's bound session.

A protected task becomes `approved` only inside the trusted issuance operation, which records the approval and the task transition together. `markPolicyEligible` can approve work that does not require an owner. `applyOwnerApproval` does not authorize protected work. `approved` does not mean `running`. Policy eligibility refuses every operation that requires owner approval. Manager, specialist, and system-policy principals cannot satisfy an owner gate. An absolute prohibition cannot be approved away. Unknown specialists and unknown operations are denied.

Budgets are capped by the canonical specialist profile. A larger allocation, a non-finite limit, a negative limit, missing usage, or usage that has reached the limit blocks execution. Repair and file-change limits of zero still allow a task that has used none of that resource. Retry and recovery do not lower recorded usage. This is a pre-execution decision over numbers the caller supplies. No usage collector or price table exists.

Recovery resumes only the same task id, idempotency key, budget, and recorded usage. The session must belong to that task and specialist, use the profile adapter, carry an external session reference, and be `starting` or `running`. The task lease must name that session and be an unexpired timestamp. A missing, malformed, expired, or other-holder lease is not eligible. Cancelled tasks and finished sessions are not eligible.

## What these checks do not establish

`assessApproval` still reports whether a caller-supplied object matches the policy shape. That match cannot authorize protected work. `evaluateExecution`, `enterExecution`, `openSession`, `confirmSessionRunning`, and `evaluateRecovery` do not accept an approval grant. Protected operations stay at `requires_approval` until `evaluateTrustedExecution` or its execution helpers re-read a trusted approval record and recompute its plan digest. `evaluateBindingGates` can report that the remaining gate is a trusted binding. That result is not authorization.

Trusted issuance checks the existing admin session cookie. `getAdminSessionUsername` verifies the HMAC and expiry. The username must also be present in `CENTRAL_AGENT_MANAGER_OWNER_USERNAMES`. There is no second authentication system. The issuer computes the plan digest on the server. A caller-supplied digest is not an input. Issuance locks the task, checks the plan version and both digests, inserts the approval, and marks the task approved in one store operation. A replay of a revoked or expired approval fails. A failure publishes neither change. The production store is `unavailableApprovalStore`, so the admin approval route fails closed. No database adapter is connected. The in-memory store is a test double, not cross-process authorization, and it does not prove PostgreSQL behavior.

The authorization digest is SHA-256, from Node's built-in `crypto`, over a key-sorted JSON document of safe integers and ASCII tokens. The unapplied SQL builds that same document from plan columns and hashes it inside the write functions. It does not store a caller-supplied digest. The digest binds the task id, plan version, specialist, authorized operation, environment, requested scope, allowed scope, budget, validation requirement, profile isolation, and profile prohibitions. The task fingerprint is the same document without the operation and environment. Source and target revisions are explicit nulls because `SupervisorTask` has no revision fields. A future engineering handoff must add verified revisions before that handoff is authorized. Reordered scope lists produce the same digest. A change to scope, budget, operation, environment, specialist, or version produces a different digest when `planVersion` stays the same. Budget values that are not safe integers are rejected.

Logout clears the admin cookie. There is no server-side session denylist, so a copied cookie remains valid until its embedded expiry. Revocation sets `revokedAt` through a separate operation and cannot be cleared. The unapplied SQL in `sql/central-agent-manager-approvals.sql` is not a migration. Its constraints and triggers do not stop a database administrator who can replace functions, disable triggers, or alter roles. The proposal does not create those roles or change any live grant. The executor role cannot mint or revoke approvals. `owner_username` is an attestation from the approval-authority role, not cookie proof. There is still no usage meter or lease issuer.

A future approval connection must call `assertApprovalIssuancePermitted` with `session_user`, `current_database()`, and `neon.branch_id` from the same session, and the SQL write functions call `assert_session_identity()` before writing. It must not use `getSql()`. Those checks are not called by the approval route. Memory-store tests do not open a database.

Evidence checks are structural. Verified completion requires executor-sourced `work_completed` for the bound session, plus validator-sourced `validation_passed` when the profile requires validation. Model success claims and failure records are stored as unverified. Nothing here signs evidence or proves the named source produced it. Diagnostics are scrubbed for known secret patterns and limited to 240 characters. They are not a retained raw stdout or stderr stream, and pattern scrubbing does not find every sensitive string.

The task object is the caller's record. These functions revalidate the object they receive. They cannot see a later mutation, a second session, or a database row they were not given. Replacing both scope arrays, forging a lease, or inventing an external session reference is outside this module's proof. Adapters must call `enterExecution` or `confirmSessionRunning` with the current task, approval, usage, isolation, and clock immediately before work starts, and must recheck the budget before every usage increment. Lease issuance and fencing are not implemented.

Staging status risks are unchanged and out of scope: the Preview role is still `neondb_owner`, the status route does not prove the database host or Neon branch before connecting, and a missing branch override can fall back to the shared Production database. The approval route does not use that path.
